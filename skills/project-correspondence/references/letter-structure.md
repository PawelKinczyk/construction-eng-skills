# Document formats and tone

## 1. Common head block

Every outgoing document starts with the same block. Headings go in the deliverable language.

```
Number: <project prefix>-<type>-<sequence>        Date: <YYYY-MM-DD>
From: <company, department, person, role>
To: <company, person, role>
Copy to: <engineer, site manager, planner>
Our reference: <earlier document number, if any>
Their reference: <the document being answered, if any>
Subject: <one line, specific, no adjectives>
Attachments: <numbered list, each with title, revision and date>
```

Rules
- The subject line states the subject, not the feeling: "Brak rzutu kanalizacji podposadzkowej - wpływ na termin" not "Kolejny problem z dokumentacją".
- One subject per document. If a second subject appears, write a second document.
- Attachments are numbered, and each is referenced in the body where it is used.

## 2. Letter

```
1. Opening: what this letter is about, in two sentences, with the reference chain.
2. Facts: what happened, when, in what document, with what consequence.
3. Request: what is needed, from whom, by when, and why that date.
4. Reservation: what is reserved, under which clause, if relevant.
5. Closing: one sentence, and the signature block.
```

Length: one page unless the facts need more. Longer letters are read only by the people who already agree.

## 3. RFI / technical query

```
Number, date, from, to
Document affected: <drawing / specification / BOQ>, revision, page, clause, position
Question: <one question, answerable in writing, yes/no or a value where possible>
Our position / proposal: <optional, and clearly marked as a proposal, not a question>
Why it matters: <consequence for design, cost, programme or safety>
Needed by: <date> because <reason>
```

Rules
- One question per RFI. Ask yes/no questions where the answer is a decision.
- Quote the wording being questioned briefly, with the reference. Do not paraphrase the specification and then question the paraphrase.
- Ask for a written answer, and say that work is on hold for that part if it cannot proceed without it.
- Track the answer in the register, including the answer document number.

## 4. Transmittal

```
Number, date, from, to
Documents issued: list of title, number, revision, status, format, quantity
Purpose of issue: for information / for approval / for construction / for record / as built
Action required and by when: <or "for information, no action">
Condition of issue: <stated where relevant, for example "not for construction">
```

Rules
- State the purpose. An issue "for information" that is later built from is a classic dispute; label it.
- List every sheet or file. A transmittal with "as discussed" and no list is not a transmittal.
- For purpose "for approval" the transmittal always carries the line "Not for construction until approved" (in the document language, e.g. "Nie do realizacji do czasu zatwierdzenia"), in the condition of issue.
- Keep the revision and status codes exactly as they are in the project standard.

## 5. Contractual notice

```
Number, date, from, to
Contract clause: <clause number as printed in the contract documents>
Event: <what happened, when, where>
Notice: <that this is a notice under that clause, and what it concerns>
Effect: <time, cost, or both, and "not yet quantified" where it is not>
Information supplied: <what is attached, what will follow>
Reservation of rights: <explicit sentence>
```

Rules
- Give the notice you are required to give, in the form the contract requires. A court or a tribunal reads the notice, not the intentions behind it.
- Record the sending date and the delivery method. Where the contract requires a specific channel (portal, registered post, engineer's address), use it and keep the proof.
- Send notices inside the time bar. Late is late, whatever the merits.
- Do not quantify a claim before it can be quantified accurately. State that quantification follows.

## 6. Change request / variation

```
Number, date, from, to
Reference: instruction or event that triggered it
Change described: what is different from the contract scope
Reason: why the change is needed, with documents
Effect on design: documents to be revised and by when
Effect on programme: activities affected, allowed or not yet known
Effect on cost: priced / to be priced, with the basis
Effect if not approved: what happens to the programme or the scope
Decision needed by: <date>
```

Never present a change as already instructed unless an instruction exists, with its number and date.

## 7. Non-conformance / defect report

```
Number, date, from, to
Location: building, level, room, grid, drawing
Element and trade
Description of the non-conformance, with photos and measurements
Requirement it fails: document, clause, test
Immediate action taken, if any
Proposed disposition: repair / replace / accept (with the technical justification)
Response needed by: <date>
```

Never propose acceptance of a non-conformance in the same document that reports it without a technical justification.

## 8. Coordination issue report

```
Number, date, from, to
Clash or interface: the two (or more) elements, disciplines, documents
Where: level, area, grid, drawing and model reference
Who is affected and what stops
Options: one to three, with the cost or programme effect of each
Recommended option, and by whom the decision is needed
Decision needed by: <date>, with the reason for that date
```

## 9. Tone rules

- Facts and requests, no adjectives about people or companies. No "as you should know", no irony, no blame.
- Write for a reader who is not on the project: full document numbers, dates, no internal slang.
- Short sentences, active voice. Say who does what by when.
- State a consequence once, factually. Repeated threats weaken the position and annoy the reader.
- Never write anything that admits liability, unless the responsible person has decided to admit it.
- Name the reason a date matters: a delivery, a cure period, a season, a milestone, or a third party's deadline.
- Numbers, units and dates in the project's conventions (see the jurisdiction file).
